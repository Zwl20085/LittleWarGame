# LittleWarGame 开发交接与验收

目的：让后续开发 agent 能明确“做什么、谁负责、如何判定做对”，避免把策划文字自由改成另一个游戏。当前仓库无游戏实现，本文没有宣称任何功能已运行。

## 1. 开工前先读什么

先读 `README.md` → `GAME_DESIGN.md` 第 1—5 节 → 本文件 → 与当前任务相关的 `BALANCE_SPEC.md` 全部规则 → `VISUAL_UX.md`。

明确的产品决定：电脑横屏，30—45 分钟，精致哑光微缩沙盘，二战作战室 UI，分层 HUD，默认公开沙盘、可选迷雾，默认自动但可框选细操。45° 俯视是用户提出的可考虑方向，按推荐初值实现可调相机，不能描述成用户要求固定锁死。

后续不得自行新增强制经济微操、大战略回合、卡牌抽取、联网账号、付费系统、固定国家科技树或只能两方交战的数据结构。引擎、编程语言和资产管线目前未选，不要把本文当作已有技术栈。选择引擎前根据真实地形高差、实体抛射物、桌面输入、可测 AI 和内容制作成本做短原型比较，不因仓库名推断一定是网页游戏。

文档不是 `AGENTS.md`，不自行授予外部发布或多人代理权限，也不要求开启多个开发 agent。每个实施任务以用户授权和仓库规则为准。

## 2. 数据层与模拟边界

推荐结构：

```text
用户输入 / AI 意图
         ↓
CommandBus（校验、记录、按 tick 执行）
         ↓
固定步长世界模拟
  资源 / 生产 / 导航 / 单位 / 武器 / 投射物
  补给 / 士气 / 工事 / 敌情 / 占领 / 胜负
         ↓
事件总线 + 只读世界快照
         ↓
渲染、模型动画、粒子、音频、HUD、战线叠层
```

模拟不依赖 UI 控件状态、动画结束回调或当前相机。UI 发命令，不直接增减资源/HP。动画迟一帧不能延迟炮弹发射；烟雾粒子被裁剪不能改变真实烟幕 LOS。所有模拟实体持久 ID，阵营为任意整数 ID。

CSV/JSON 需要加载校验：ID 唯一、单位武器引用存在、设施有效、成本非负、HP>0、人口>0、重力>0、最大射程≥最小射程、同一 PRNG 不与视觉共用。加载失败说明哪一行/字段；不得静默用 0 代替缺字段。

当前种子数据不会覆盖全部战斗系数。实现阶段把数值文档里尚未进 JSON 的命中、掩体、装甲、地形、士气和散布系数统一补进版本化配置；不要在系统代码里散落魔法数。新增 schema 须更新说明和配置校验。

## 3. 核心对象最小字段

| 对象 | 必需字段 |

| FactionState | id、存活、P/M 浮点库存、劳动力份额/锁定、意志、人口在场/预占、L、生产规则、节点收益 |
| SectorPlan | id、owner、目标/集结点、姿态、增援份额、预算、供给优先级、当前执行原因 |
| UnitState | id、owner、unitType、位置/朝向、HP、Q/S/A、状态/剩余时长、武器冷却、供给、sectorId、手动任务 |
| ProductionOrder | id、owner、unitType、目标战区、设施位、状态、剩余工时、扣款事务、人口预占、出场状态 |
| Projectile | id、owner、weaponType、起点/速度/飞行时间、上一位置、碰撞状态、伤害结算标记 |
| ~~AirMission~~ | v1.0 已移除空军系统 |
| Objective | id、类型、位置、owner、争夺状态、各方进度、启用计时、连通性 |
| Fortification | id、类型、owner、位置/朝向、HP、建设进度、容量/占位、是否可导航障碍 |

班内视觉士兵 ID 可附着于 UnitState，但不成为独立计费/占领/意志实体。所有 UI 敌情字段必须经过观察者可见性过滤，不能直接绑定全世界敌单位 HP。

## 4. 关键接口与语义

### 4.1 命令

建议命令 envelope：`commandId, issuedTick, actorFactionId, type, payload`。支持：设置出兵规则、单次生产、暂停/取消订单、设置劳动力、切换托管、设置战区、重整战区、单位移动/攻击移动/集火/撤退/固守/恢复自动、炮击区域、空军任务、规划工事、暂停/速度。

校验：阵营存活且拥有对象；目标存在/信息允许；库存和人口足够；点可达；类型/模式支持。失败返回结构化 reason，如 `INSUFFICIENT_M`、`POP_RESERVED_FULL`、`NO_LOS`、`STALE_TARGET`、`UNREACHABLE`，并提供 UI 参数，不能仅返回 false。

暂停/速度属于本地比赛控制；暂停时命令可记录到恢复后的下一 tick。相机、面板、选中与 UI 缩放不进入战斗命令日志。

### 4.2 经济事务

唯一入口 `TrySpend(faction, p, m, reason, transactionId)`；退款同样事务化。检查—扣款—人口预占是一个原子动作，不分散到不同 tick。订单完成时只转换人口分类，不再扣成本；重复完成事件幂等。

劳动力保持总和 1，锁定项不得被托管改；手动输入超出总和时 UI 做守恒分配并预览结果，模拟仍校验。界面显示整数资源，逻辑保留小数。

### 4.3 导航、LOS 与火力

`FindPath(unitType, start, goal, knownThreats)` 返回路径/失败原因；导航可行性使用真实地形，威胁代价只使用当前情报。局部避让不允许双方单位长时间交叠；不能为了解卡死把单位任意瞬移到敌后。

`CanObserve(observer, target)` 与 `CanFire(weapon, shooter, target)` 分开：看得见未必打得着，炮兵可以凭合法记忆打区域。直射 LOS 用炮口/观察点高度，最低射程、架设、朝向与俯仰分别校验。

`LaunchProjectile` 创建真实飞行状态；`ResolveImpact` 是唯一 HP 结算入口。直接命中概率先生成瞄准偏移：成功以合法弹道朝当前目标点；失败以确定的偏移方向飞行，不再在碰撞时二次抽 pHit。目标可以在弹体抵达前移动躲开，未命中弹可以撞到其他目标。

AP 主命中与 HE 邻近列表去重，主要目标不同时承受两份同发伤害。hitscan 命中只结算一个事件，曳光是表现；ballistic accuracy 字段 0 表示不用直射命中概率，并非“无法命中”。弹体 sweep 检测与地形采样使用同一碰撞语义。

### 4.4 目标选择

先得到武器可攻击候选，再给各项归一化到 0—1：

```text
score = 0.30*threat + 0.25*weaponSuitability + 0.20*objectiveRelevance
        + 0.15*distancePreference + 0.10*targetContinuity
```

武器适配取角色矩阵：机枪偏步兵、反坦克偏车辆、防空有可行飞机时优先飞机、炮兵偏固定阵地和集群。只有攻击当前目标明显不可能或自卫危险时可跳过保持期。调参应能在调试面板看到候选评分，便于解释追车、转圈或不射击。

### 4.5 战线与信息过滤

真实地面控制场供后勤阻截和调试使用；可展示的战线按观察阵营过滤；两者不能混用。公开模式使用完全态势，迷雾模式使用可见/记忆态势，观战者可以全知但无指挥权限。

关系矩阵用于所有武器目标、占点、伤害与防空。自动避免误伤是决策行为，不是关系矩阵禁止对友军伤害。

## 5. 每 tick 建议顺序

1. 执行当前 tick 已校验命令；处理订单/成本事务。
2. 到期的城市/战区/单位 AI 读取上个稳定状态，生成本 tick 意图。
3. 更新移动、车体/炮塔朝向、架设/收起与路径状态。
4. 更新可见性及到期的补给网络/份额，计算攻击资格。
5. 处理攻击、耗弹和发射；同 tick 的目标毁灭不剥夺已经合法发出的弹体。
6. 更新投射物与飞机投放，收集碰撞与命中事件。
7. 稳定排序事件、结算伤害/压制/士气、移除死亡，释放人口与意志损失。
8. 更新恢复、弹药补充、占领、节点收益、生产工时与合法出场。
9. 结算多数控制意志流失、城市淘汰和胜负。
10. 到期更新影响场，发出快照/表现事件；按计划保存校验。

双方同 tick 指挥部完成占领或意志归零时先收集全部淘汰，再判断存活者；若无人存活，结果为共同毁灭/平局，不让遍历顺序决定赢家。生产与经济的 1 秒结算必须采用统一固定时间点，而不是看渲染帧是否越过整数秒。

可根据引擎实现调整内部顺序，但必须固定、可记录，并为首发命中、同时死亡、飞机先投弹还是先被击落等争议场景定义一致规则。

## 6. 实施顺序与交付

### M0：基础交战

交付可运行灰盒、1v1 地图、完整单位/武器加载、固定 tick、步兵/机枪/反坦克/轻坦、先头部署、生产、简单进攻 AI、城市占领/意志胜负。相机从第一天使用有高差的地形和斜俯视，避免平面版本完成后返工。

至少证明：生产真的扣资源，双方真的按射界开火，步兵能占领，坦克不会被步枪磨死，同等局能够结束。此时可简化局长，不作为最终 30—45 分钟体验验收。

### M1：可统筹也可观战

完成托管、完整出兵调度、战区姿态、手动覆盖层、主面板、弹药/补给、撤退/恢复、战线。用户只动出兵和战区也能完成比赛；手动框选不会永久破坏自动任务。

### M2：阵地与立体火力

完成间接弹道、真实高差 LOS、掩体方向、压制/士气、工兵、野战掩体与堡垒、中重坦/榴弹。先用专用测试地图证明跨山/遮挡，再到主图调节 AI。

### M3：全部需求闭环

完成实体空袭/防空、4 方 FFA、公开/迷雾双模式、全功能结算、存读/回放、基础精致沙盘与作战室 UI。不能把“配置里写了 factions=4”当作支持多方，必须实际进行四方生产、目标选择与淘汰。

### M4：验证与打磨

完成回归场景、成批 AI 局、输入与遮挡 QA、模型/音效、美术 LOD、压力测试。交付配置版本、测试结果、已知限制与下一步。30—45 分钟目标须用正常速度游戏时间验证，不拿 4× 下 10 分钟的实时间混淆。

每阶段提供简短运行说明和真实演示路径，注明已做/未做。不要提前生成虚构测试胜率，也不要把演出效果说成已经有对应模拟规则。

## 8. 性能预算与调试工具

参考场景：1920×1080、4 阵营各人口 80，最多约 160 个纯步兵战术实体/1280 个显示士兵，另加守备、飞机、工事和投射物。测试压力项可以设 200 个战术实体、300 枚在飞弹体；这高于一般实战，不是承诺所有电脑都能达到。

目标在约定测试机上 1× 常规 60 FPS；固定模拟 20 Hz 单 tick 平均预算目标 ≤8 ms。4× 每渲染帧的 tick 数增长，应记录最坏 tick 和输入延迟，不能默认仍有同等性能。测试机规格在实施时记录实际硬件、引擎版本与分辨率，不虚构已有基准。

优化顺序：空间索引筛选目标/爆炸范围 → 分批 AI 更新 → 缓存导航/LOS → 班级模拟与视觉 LOD → 粒子/阴影控制。性能不够先降低视觉量，不降低攻击准确性或暂停某方 AI。模拟追赶不能静默丢 tick；如果需要自动降速，界面必须说明。

开发调试叠层至少显示单位状态机、目标评分、路径、LOS、架设射界、供给边与比率、经济事务、人口账、炮弹轨迹/落点、可见性、真实/估计战线、AI 目标和阻塞原因。调试控制在发布默认关闭。

## 9. 内容与资源交付

首版装备名称先使用功能兵种，不硬绑真实国家型号。年代装备细分可采用中后期二战语汇，但需单独与用户确认；本次没有授权复制现有游戏模型、贴图、UI 或受版权保护资产。

引入模型、字体、音效时记录来源与许可，统一单位比例、模型前向、炮口挂点、车体/炮塔分离、阴影与材质要求。资源缺失以明确灰盒替代并记录，不隐藏缺失。

后续任务可以分别聚焦模拟、单位 AI、城市生产、战场表现或 UI，但必须通过同一命令/数据接口连接。改变字段与系统语义时先同步其他模块消费者和文档，避免各自实现不同的 HP、人口、角度和阵营定义。

## 10. 修改原则

用户的最新明确选择优先；数值调整以实测为依据；新功能与未来扩展分开；不要为短期演示绕过资源、补给、命中或迷雾。最终交付需要说清实现范围和测试证据，不能把这份策划稿当作已经实现的游戏。
