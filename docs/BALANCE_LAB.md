# 数值实验室（Balance Lab）——数值调试流程

> 目的：资源、生产、战斗、伤害、HP 之间的关系不能靠"看一局感觉"来调。每次改数值都先用实验室跑**同一批种子**的无头 AI 对局，读指标、看哪一条约束在起作用，再改，再跑，把前后差异贴进 PR。

实现：`scripts/lab.ts`（入口）+ `scripts/lab/*.ts`（覆盖、探针、汇总、报告）。实验室**只读**世界状态，不写任何字段，因此实验对局与正式游戏的确定性对局完全一致（同种子、同数据 → 同结果）。

## 1. 怎么跑

```bash
# 当前数据，3 个种子 × 20 分钟（默认 7,11,13 × 20）
npx tsx scripts/lab.ts --seeds 7,11,13 --minutes 20

# A/B：基线 vs 修改，同种子，输出差异表
npx tsx scripts/lab.ts --seeds 7,11,13 --minutes 30 --ab --set territory.capital_income_share=0.15

# 一次比较多个方案（每个 --vs 是 "名字:覆盖1;覆盖2"），--ab 额外跑未修改的基线
npx tsx scripts/lab.ts --ab --vs "cap10:territory.capital_income_share=0.1" \
  --vs "town50:territory.income_p_per_min.town*=0.5;territory.income_m_per_min.town*=0.5"

# 某个方案本身当基线：把它命名为 baseline
npx tsx scripts/lab.ts --vs "baseline:proposed_defaults.tempo_damage_multiplier=1.8" --vs "x:..."
```

| 参数 | 含义 |
|---|---|
| `--seeds a,b,c` | 种子列表；至少 3 个种子才下结论 |
| `--minutes T` | 每局模拟时长（游戏分钟）；经济稳态问题至少 30 分钟 |
| `--warmup W` | 速率类指标排除前 W 分钟（默认 `min(5, T/3)`） |
| `--set path=value` | 覆盖（可重复），见 §2 |
| `--vs "名:覆盖;覆盖"` | 额外方案 |
| `--ab` | 同时跑未修改的基线并输出差异表 |
| `--label 名` | 报告文件名标签 |
| `--map generated\|four_cities`、`--factions 4`、`--difficulty normal` | 对局设置 |
| `--src 目录`、`--data 目录` | 模拟源码根目录与数据目录（默认 `src`、`docs/data`）。多人同时改代码时可先 `cp -r src docs/data media/labsrc/` 冻结一份，保证 A/B 用同一份代码 |
| `--jobs N` | 并行子进程数（默认 CPU 数 − 2；每个种子×方案一个进程） |

输出：控制台摘要 + `media/stats/lab-<label>-<时间>.md`（人读）与 `.json`（全部 30 秒采样、每分钟约束计数、易手事件，便于再分析）。`media/` 不入库，结论请贴进 PR 或本文 §5。

耗时参考（16 核）：20 分钟局约 3—5 分钟/局，各局并行。

## 2. 覆盖语法

覆盖作用在**原始数据文本**上，再走正式加载器与校验，所以和改文件完全等价；路径写错直接报错，不会"静默无变化"。

| 目标 | 写法 | 例 |
|---|---|---|
| rules.json | `路径=值`（可加 `rules.` 前缀） | `economy.cap_p=1000`、`morale.auto_retreat_hp_ratio=0.2` |
| units.csv | `unit.<id 或 *>.<列>=值` | `unit.infantry.cost_p=90`、`unit.*.build_seconds*=0.8` |
| weapons.csv | `weapon.<id 或 *>.<列>=值` | `weapon.rifle.damage=40` |
| 运算 | `=` 赋值、`*=` 乘、`+=` 加 | `weapon.*.damage*=1.2` |
| 通配 | 路径段 `*` = 该对象所有键 | `territory.income_m_per_min.**=0.5`（即 `.*` 加 `*=`） |

注意：rules 中的数值是 `army_scale=1` 的种子值，加载时由 `src/sim/scale.ts` 放大（人口、库存上限、产能 ×10 等；收入 ×10×0.25）。

## 3. 指标与验收带

速率类指标只统计热身之后；"pooled" = 所有种子、所有存活阵营的平均。

| 指标 | 定义 | 意义 | 验收带 |
|---|---|---|---|
| 部队满员度 fullness | 人口（在场+在产）/ 人口上限，均值 | "永远满编"就是它接近 1 | **0.55—0.85**（1.0 第二轮：进攻期应跌破 0.6） |
| 满员度最小值 | 同上，最小值 | 攻势中应该被打下来 | 0.40—0.80 |
| 库存/上限、P 库存/上限、M 库存/上限 | 各自比例 | 哪种资源在堆 | — |
| 库存可支出分钟数 stockMinutes | 当前 P+M 库存 ÷ 最近 5 分钟平均每分钟支出 | 囤积程度；大于 3 说明钱花不出去 | **≤ 3** |
| 囤积比 hoard | 库存 ÷ 5 分钟支出 | 同上的另一种刻度 | ≤ 0.6 |
| 收入 / 支出 | P+M 每分钟 | 支出/收入 < 1 且库存增长 = 钱没处花 | — |
| 约束分类 binding | 每阵营每秒判断"为什么现在不再多造"：**pop** 人口满；**slots** 所有相关生产位都忙；**resources** 有空位但买不起（含高价订单保护预留）；**free** 有空位也买得起（调度器下一秒就会开工）；**caps** 全部兵种达到计划上限 | 回答"到底是资源、产能还是人口在卡" | resources ≥ 35 %、pop ≤ 30 % |
| 缺 M 占比 resMShare | resources 秒数中是军需（M）不足的比例 | 区分兵员 P 还是军需 M 是瓶颈 | — |
| 生产位占用 | 在产订单 / 生产位 | 产能是否过剩 | — |
| 损耗率 attrition | 每分钟损失单位数 / 每 100 个战斗单位 | 损失是否"有感" | **4—15** |
| 每分钟损失价值 | P+M | 和收入对比：稳态时收入 ≈ 损失价值 + 少量增长 | — |
| 补充时间 | 部队总价值 ÷ 每分钟支出 | 全军覆没后多少分钟能重建 | — |
| 伤害/分钟 | 本方造成的 HP 伤害 | 交战强度 | — |
| 撤退中比例、开火比例、平均 HP | 战斗单位中处于 retreat/recover/routing、5 秒内开过火的比例 | 损失低是"打不死"还是"没在打" | — |
| 据点数、净增、首次占领时间、每分钟占领数、失去据点数、易手次数 | village/town/city（不含 point） | 领土争夺是否活跃 | 首占 ≤ 4 分钟、占领 ≥ 0.15/分钟 |
| 积极性 eagerness | ① 战斗单位中 opRole 为 occupy/garrison 的比例；② 各战区（编组）重心到最近可夺据点的距离（按人数加权） | 指挥官对领土的"渴望" | — |
| 兵种账本 | 造/损/击杀、K/D、每单位每分钟伤害、击毁价值/花费 | 哪个兵种是钱的黑洞 | — |
| 击杀矩阵 | 攻击者 × 受害者 | 克制关系 | — |
| 时间线 | 每 5 分钟：人口/上限、P/M 库存与收入、单位数、据点数、累计损失、开火比例 | 看趋势，不只看均值 | — |

`bind/min` 一行是每分钟主导约束（P/S/R/./C），例如 `SRRRRRRRPPPP` 表示开局产能卡、中期资源卡、后期人口卡——这正是"后期永远满编、钱堆起来没用"的典型形状。

## 4. 流程规则

1. **改数值前**先跑基线（≥3 种子；经济问题 ≥30 分钟），保存报告。
2. 每次只改一小组**可归因**的参数，用 `--ab` 或 `--vs` 同种子对比。
3. 先看约束分类和时间线判断是哪一环，再动对应杠杆：
   - 人口卡（P）且库存涨 → 收入相对损失过高：降收入或提高损耗，而不是提人口上限。
   - 产能卡（S）→ 加生产位或缩短工时。
   - 资源卡（R）但损耗低 → 部队在增长，检查是否没在交战（开火比例）。
   - 损失低：开火比例低 = AI/行为问题；开火比例高但 HP 均值高 = 伤害/HP/撤退阈值问题。
4. 行为问题交给 AI 负责人，经济问题改收入/成本，最后才改伤害（与 BALANCE_SPEC §11.3 一致）。
5. **改完再跑**；PR 必须贴 A/B 差异表（报告中 "A/B diff" 段）和验收带结果。没有前后对比的数值改动不合并。
6. 同步修改 `docs/data/*` 与 `BALANCE_SPEC.md` 的对应数字。

## 5. 实验记录

### 2026-10-03 第一轮：诊断"永远满编、资源没意义"

代码快照：2026-10-03 工作区（空军删除进行中），地图 generated、4 方、normal，种子 7/11/13。

#### 5.1 诊断（旧数值，40 分钟）

| 指标 | 值 | 解读 |
|---|---:|---|
| bind/min | `S RRRRRRRRRRRRRRRR PPPP…P` | 开局 1 分钟产能卡，1—17 分钟资源卡，**17 分钟后人口卡直到结束** |
| 生产位占用 / slots 约束 | 0.15 / 0 % | **产能不是瓶颈**，生产位约 85 % 空闲 |
| 满员度均值 | 0.94 | 后期 558/558 |
| 库存（35 分钟） | P 5380 / M 4445（上限 6000/4800） | 人口满后钱无处可花，支出/收入 0.54 |
| 收入增长 | 700 → 2450 P+M/分钟 | 开局约 119 个中立村镇，占领一路推高收入与人口上限 |
| 损耗率 | 3.45 / 分钟 / 100 单位 | 每分钟损失价值 466，仅为收入的 21 % |
| 开火比例 | 0.08 | **9 成以上的部队不在交战**；`line` 角色约占一半 |
| 撤退中 / 平均 HP | 0.07 / 0.90 | "打不死"不是主因；没在打才是 |
| 榴弹炮 | 造 235、损 7、击毁价值/花费 0.02 | 钱的黑洞（AI 不前送，见 §5.4） |

结论：经济目标应是"稳态收入 ≈ 损失价值 + 少量增长"。旧数值收入约为损失的 5 倍，所以部队单调增长到人口上限，资源随即失去意义。提高伤害对损耗的弹性很低（+38 % 伤害 → +15—20 % 损耗），因为交战本身少。

### 2026-10-03 1.1 round: artillery and unit identity（加强炮兵 + 兵种身份核对）

用户要求："加强炮兵"；"核对每个单位的伤害/HP 是否符合名字给人的印象，但游戏性第一"。约束：炮兵不能主导战场；坦克是进攻矛头；反坦克炮是挡坦克的东西；城镇值得防守；战争仍要能结束。

代码快照：v1.0.0（HEAD 3996f00）的 `src` 与 `docs/data` 冻结到 `media/artlab/`，所有 A/B 在同一份代码上跑（其他 agent 同时在改 AI 与性能文件）；最后再在当时的工作区快照上复核。地图 generated、4 方、normal。

#### 5.5.1 测量：炮弹为什么打不死人

在冻结代码的副本里加探针（只读，结果与未加探针时逐位相同：损耗率 5.70），记录每发间接炮弹的目标、散布、计划落点、实际爆点、飞行时间、对敌/对己伤害，以及炮兵每 tick 的状态。种子 7/11/13 × 30 分钟：

| 每发炮弹（原始伤害，未乘 tempo 1.8） | 榴弹炮 | 迫击炮 |
|---|---:|---:|
| 目标正在移动的比例 | 92 % | 85 % |
| 平均 sigma（米）/ 有观察的比例 | 23—28 / 22—32 % | 8—12 / 50—84 % |
| **实际爆点离计划落点**（米） | **74—142** | 1—2 |
| 0.3 秒内就爆炸（炮口附近）的比例 | **≈ 21 %** | < 1 % |
| 低弧被挡、改用高弧的比例 / 高弧飞行时间 | 10—28 % / **19.6 秒** | — / 12 秒（只用高弧） |
| 对目标伤害 / 对**己方**伤害 | 5.1 / **6.1** | 0.1 / 0.3 |
| 炮兵时间：转移中无目标 / 架好开火 | 42 % / 26 % | 73 % / 15 % |

原因（按影响排序）：

1. **炮弹在自己炮位爆炸**。`arcClear` 的 0.1 秒步长从炮口外 6—10 米才开始采样，贴着房屋或面朝上坡的炮能通过检查；约 21 % 的榴弹在 0.3 秒内撞墙/撞坡，另有约 10 % 撞上沿途山脊（旧规则："两条弧都被挡也照样开火"）。爆点在己方阵地上，所以对己方伤害（6.1）比对敌（5.1）还高。基线账本里"榴弹炮击毁榴弹炮 21 次"大多是这种误伤（友军击杀也记在攻击方兵种名下），并不是反炮兵。
2. **对移动目标不加提前量**。迫击炮高弧飞 12 秒、榴弹炮低弧 5 秒（高弧 20 秒），2.9 m/s（1.6 × tempo 1.8）的步兵在落弹前已走出 15—45 米，而爆炸半径只有 8—12 米。
3. **散布远大于爆炸半径**。闭式期望 `E[falloff] = 1 − (1 − e^{−R²/2σ²})·2σ²/R²`：σ=26、R=12 时 ≈ .05，即每发对目标约 125×.05 ≈ 6.5 原始伤害——与实测 6.8 吻合。对 800 HP 的步兵班需要 60 多发。
4. **AI 用法**（不在本轮范围，已交 AI 负责人）：迫击炮 73 % 时间在没有目标地转移；AI 把榴弹炮造满上限（每方约 17 门，花费与可打目标不成比例）。射击—转移（6 轮后挪 80 米）只占 0.5 % 时间，不是原因；弹药也不是。

#### 5.5.2 规则修正（`src/sim/ballistics.ts`、`combat.ts` 炮兵部分、`config.ts`）

| 规则 | 旧 | 新 |
|---|---|---|
| 炮口前遮挡 | 0.1 秒步长，6—10 米外才检查 | 炮口前 24 米每 1.5 米采样（`MUZZLE_CLEAR_M`）；贴墙的炮 `canEngage` 得到 NO_ARC，AI 换阵位 |
| 两条弧都被挡 | 照样开火（撞山） | 不开火（`status.noArc`），下一 tick 重新抽散布落点 |
| 移动目标 | 瞄准当前位置 | 瞄准 `位置 + 朝向 × speedNow × 飞行时间 × 0.8`，最多 60 米（`DISPERSION.leadFactor/leadMaxM`） |

仅规则修正（数值不变）：榴弹爆点误差 74—142 → 7—24 米，对己方伤害 6.1 → 0.3/发，对目标伤害 5.1 → 6.7/发；效率几乎不变（0.20 → 0.14，迫击 0.02 → 0.07），因为第 3 条原因（散布 ≫ 半径）仍在。每 tick 成本：只多一次 `solveArc`（提前量，仅开火时）和每次弧检查 ≤16 个采样；实验室墙钟时间不变。
